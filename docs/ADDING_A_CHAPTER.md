# Adding the next chapter

The app shell (screens, renderer, playback and progress) reads all content from the chapter registry. To add a chapter you add data, not screens.

## 1. Add the legal sources

1. Add new rule IDs to the `RuleId` union in [`src/content/types.ts`](../src/content/types.ts).
2. Add a `RULES` entry for each rule in [`src/content/rules.ts`](../src/content/rules.ts). Include the official text (verbatim, from the current consolidated version) and a plain-language Georgian paraphrase.
3. Add `SOURCE_REGISTER` rows with `reviewStatus: 'draft'` until you have compared them with the source. Only a real qualified reviewer may set `instructor_reviewed`.
4. Add the rule IDs to `RULE_IDS` in [`src/progress/storage.ts`](../src/progress/storage.ts) so stored attempts validate.
5. Update [`docs/SOURCE_REGISTER.md`](SOURCE_REGISTER.md).

## 2. Author the scenarios

Create `src/content/chapters/<chapter-id>/scenarios.ts`. Each `Scenario` must define:

| Field | Notes |
|---|---|
| `id`, `version` | Unique ID. Bump `version` whenever the meaning changes; old attempts are then ignored. |
| `chapterId`, `ruleId`, `mode` | `lesson`, `guided`, `independent` or `alternate` |
| `promptKa`, `roadStatusKa`, `questionKa` | State each vehicle's approach, direction and maneuver. For equal roads, say so explicitly. |
| `vehicles` | `approach` arm, `maneuver`, `body`, `color`, `appearanceKa`. Exactly one `isLearner`. |
| `roads` | `{ kind: 'equal' }` or `{ kind: 'main', mainArms: [a, b] }`. Non-opposite arms mean a bending main road. |
| `signs` | Usually generated by `prioritySigns(roads)`. Each sign faces the driver on its `arm`. |
| `options`, `correctOptionId`, `explanationsByOption` | A specific explanation for **every** option, never a generic "incorrect". |
| `conflicts`, `highlight` | Which paths cross; who has priority; decisive signs; optional relationship line. |
| `source`, `reviewStatus`, `authorNotes` | Explain why the layout was chosen and what it tests. |

Hand-author every variation. Never randomise roads, signs or maneuvers. Compute "right" and "left" from each driver's heading with `relativeSide()`, not from screen position.

If a chapter needs geometry beyond a four-way junction with one lane each way (roundabouts, multi-lane roads, trams), extend [`src/engine/geometry.ts`](../src/engine/geometry.ts) with new path builders. The renderer draws whatever paths the engine produces.

## 3. Write the manifest

Create `src/content/chapters/<chapter-id>/manifest.ts` exporting a `ChapterManifest`: titles, simplified conditions, `ruleIds`, `lessons` (explanation + up to three points + a lesson scenario), `guidedIds`, `independentIds`, `alternateIdsByRule`, and `scenarios`.

## 4. Register it

Append the manifest to `CHAPTERS` in [`src/content/registry.ts`](../src/content/registry.ts). The current UI shows `ACTIVE_CHAPTER`. With several chapters, add a chapter picker on the start screen and pass the chapter through the routes; the screens already take everything else from the manifest.

## 5. Verify

```bash
npm test
```

The content tests run `validateChapter()` on every registered chapter. They check unique IDs, vehicle references, per-option explanations, sign/road consistency and rule coverage. The timeline tests build every scenario's motion and check that correct replays are collision-free and that wrong-answer previews stop before the conflict. Extend `expectedPriority()` in `content.test.ts` when a chapter introduces new relationships.

Then walk through the chapter in the browser: every option, every replay, and mobile width.

## Future driver-perspective view

`Scene` (top-down) consumes a scenario, its `ScenarioMotion` (paths and timelines) and sampled positions. A driver-view renderer would consume the same inputs and the same playback state. Add it only as a genuine authored perspective illustration that shows the same signs and vehicles, never as a rotated top-down scene.
